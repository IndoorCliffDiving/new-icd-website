# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A static single-page marketing site for Indoor Cliff Diving (a diving/climbing club in Amsterdam). There's no framework or SSG — the site is two hand-written, near-duplicate HTML documents (Dutch and English) with a small Node build step that injects a live event table before deploy.

## Commands

- Install deps: `npm install`
- Build: `npm run build` (runs `node script.js`)
- No lint is configured, and `npm test` is a placeholder (`echo "Error: no test specified"`) — there is no real test suite.

## Architecture

**Source vs. generated files** — `template.html` (Dutch, the canonical/default page) and `template-en.html` (English) are the files to edit. `output/index.html` and `output/en.html` are generated build artifacts produced by `script.js`; don't hand-edit them except as a stopgap when the build can't be run, and regenerate via `npm run build` afterward to keep them canonical.

**Build step (`script.js`)** — fetches a public Google Sheets CSV (the event calendar, URL hardcoded in the script), then fills three placeholders in each template and minifies the result with `html-minifier` into `output/index.html` / `output/en.html`:

| Placeholder | Filled with |
| --- | --- |
| `<!-- ICD_EVENT_TABLE_CONTENT -->` | `<table class="agenda">` built from the sheet (localised headings) |
| `<!-- ICD_FAQ_CONTENT -->` | the visible `#faq` accordion |
| `<!-- ICD_STRUCTURED_DATA -->` | the `application/ld+json` schema.org graph |

The same run also writes `output/sitemap.xml`, `output/llms.txt` and `output/llms-full.txt`. All of these are generated — don't hand-edit them.

**`seo-data.js` — single source of truth for facts.** NAP data, geo coordinates, opening hours, prices, services, FAQ text and per-language page meta all live here in one place, in both languages. `script.js` reads it to build the JSON-LD, the visible FAQ and the llms.txt files. Two rules follow from this:

- Change a fact (a price, a training time, the address) in `seo-data.js` *and* in the matching visible copy in both templates. Structured data that contradicts the visible page is a Google policy violation, not just an inconsistency.
- The FAQ is rendered from `seo-data.js` into both the HTML and the `FAQPage` schema, so those two can't drift.

**Event structured data** — agenda dates in the sheet are free-form Dutch text with no year ("19 t/m 21 december", "juli / augustus", "???"). `parseEventDate()` emits a `SportsEvent` only for rows with an unambiguous day + month, skipping the rest, and infers the year as the next occurrence. Adding a `Year` column to the sheet overrides that inference.

**Static assets in `output/`** — `output/css`, `output/js`, `output/img`, `output/fonts`, `output/docs`, `output/corona`, `output/html`, `output/robots.txt` and `output/CNAME` are checked-in static files, not generated by the build. Templates reference them by absolute path (e.g. `/css/style.css`, `/img/logo.png`). When adding/changing assets, edit them directly in `output/` — there's no separate source directory for them.

**Two-language structure, one page each** — Both templates are built from the same anchor-linked sections (`#home`, `#about`, `#portfolio`, `#service`, `#agenda`, `#pricing`, `#team`, `#faq`, `#contact`, `#partners`) driven by the top nav. When editing content in one template, make the equivalent edit in the other to keep them in sync. There's no shared templating/partial system — duplication between the NL and EN files is expected and intentional, *except* for the three generated blocks above.

**Language routing** — there's no server-side routing; `index.html` (NL) is served at `/` by default. An inline script near the end of each template redirects on browser language: NL → `en.html` for `en*` browsers, and EN → `/` for `nl*` browsers. Clicking a language link (nav or footer) stores the choice in `sessionStorage` under `icd-lang`, which suppresses the auto-redirect — without that, an English browser could never stay on the Dutch page. `rel="alternate" hreflang` links in `<head>` and the crawlable footer switcher are what search engines actually use; the JS redirect is a convenience only.

**Script loading** — the JS bundles at the end of `<body>` are `defer`red. Deferred scripts run in document order and jQuery's `ready()` fires as soon as `main.js` executes, so any library `main.js` depends on (e.g. the matchHeight CDN script) must be listed *before* `main.js`, not after.

**Deployment (`.github/workflows/deploy.yml`)** — triggered on push to `main`, on a schedule (every 2 hours), or manually. CI runs `npm ci && npm run build`, commits any resulting `output/**` changes back to `main`, then deploys the `output/` folder to the `gh-pages` branch (custom domain via `output/CNAME` → indoorcliffdiving.com). This means `output/` on `main` is a live, source-controlled build cache that can be automatically regenerated/overwritten at any time — don't assume a manual edit there will persist past the next scheduled run.

**External integrations** — Google Tag Manager (`GTM-TBM6RL8`); Trainin.app (`indoorcliffdiving.trainin.app`) for class sign-ups and schedules, linked directly from the templates; a public Google Sheet as the event/agenda data source consumed by `script.js`.

## Discoverability (search engines and AI agents)

The site is optimised both for classic search and for AI answer engines. When changing the templates, keep these intact:

- **Per-page `<head>`** — one `<title>`, a self-referencing `<link rel="canonical">`, the three `hreflang` links (`nl-NL`, `en`, `x-default`), `robots` with `max-image-preview:large`, and Open Graph / Twitter tags using **absolute `https://` URLs** (relative `og:image` paths don't resolve for scrapers).
- **JSON-LD graph** — `SportsClub` + `SportsActivityLocation` (the most specific type for this business) with address, geo, opening hours, `hasOfferCatalog`, `sameAs` and a `ReserveAction` pointing at the booking system; plus `PublicSwimmingPool` for the venue, `WebSite`, a combined `WebPage`+`FAQPage`, and one `SportsEvent` per parseable agenda row. Nodes are linked by `@id`.
- **`robots.txt`** — explicitly allows AI search crawlers (`OAI-SearchBot`, `Claude-SearchBot`, `PerplexityBot`, `GPTBot`, `Google-Extended`, …). Blocking these would remove the club from AI answers, so don't add `Disallow` rules without a deliberate reason.
- **`llms.txt` / `llms-full.txt`** — an llmstxt.org-format index plus the whole site as plain text, so an agent can get every fact in one fetch. Adoption of the standard is still partial and Google doesn't use it, so treat these as a supplement to good HTML, never a replacement.
- **No content behind JavaScript** — many AI retrieval crawlers never execute scripts. Everything that matters, including the agenda table and the FAQ, is in the served HTML.

There is no automated SEO check in CI. After template changes, `npm run build` then confirm the JSON-LD still parses (`JSON.parse` the `application/ld+json` block) and that no `<!-- ICD_* -->` placeholder survives into `output/`.
